The code identifier for this backend is:

```text
unified
```

Use it when an OpenAI-compatible model endpoint is already available.

## Using this backend with the terminal Agent

During `bcg setup`, API model construction can reuse the Agent's own model endpoint and API key, or use a separate endpoint:

```bash
bcg setup
# Graph server: Start and manage a local Graph server automatically
# Graph backend: API model construction (unified)

bcg
```

No separate vLLM process is required when the configured API endpoint is already available. If a server for this backend is already healthy, a later `bcg` invocation reuses it instead of starting a new one.

The Graph LLM emits each node's text, four-way stance label, entities, and
evidence references in one extraction response. Confidence values are never
accepted from the model; code derives them from role, stance, evidence, and
relations. Relation extraction remains a separate model phase.

## Server

```bash
bcg construct server unified \
  --config ~/.bcg/config.yaml \
  --model-key graph-model \
  --embedding-key embedding \
  --host 127.0.0.1 \
  --port 8848 \
  --output-dir ~/.bcg/graphs
```

## Tool Result extraction

Structured Tool Results use one bounded, history-free semantic extraction path. Configure it under `pipeline.tool_results` in `~/.bcg/config.yaml`:

```yaml
pipeline:
  tool_results:
    max_search_results: 10
    max_snippet_chars: 240
    semantic_extraction: true
    max_facts: 3
    max_semantic_calls: 12
```

Parallel Tool Results are distilled in one model request while remaining isolated by a code-owned item index. Every extracted belief retains its exact `tool_call_id` and is linked to the originating Tool Call. Raw output remains attached as evidence. After `max_semantic_calls`, later results fall back to the zero-LLM rule summary; set `semantic_extraction: false` to use that path from the start.

## Stance and entity metadata

Unified asks the configured Graph LLM to produce `asserted`, `recalled`,
`judged`, or `speculated` for every semantic node and to list its salient named
entities. Invalid or missing stance labels fall back to `asserted`; malformed or
missing entity lists fall back to an empty list. Deterministic Tool Call nodes
remain code-owned: their stance is `asserted` and their exact tool name is kept
as an entity.

<Note>
How much of the Graph gets *rendered* into the Agent's context (`full` vs `compact`) is a separate setting — see [Graph presentation](/guides/reference-agent#graph-presentation-full-vs-compact).
</Note>

## Python

```python
runner = BCGRunner(
    memory=memory,
    llm=llm,
    backend="unified",
)
```

Relevant runner controls include:

```python
evidence_mode="sentence"
incremental_merge=True
incremental_merge_threshold=0.86
verify_merge=False  # pass True or use --verify-merge to enable LLM verification
context_chars=100000
io_context_chars=6000
min_content_len=0
```

These are exposed by `observe_trajectory()` / `begin_belief_run()` and may also be configured through the unified YAML settings.

## Configuration

Model and embedding endpoint definitions live in the unified `config.yaml` model registry. Use:

```bash
bcg config
```

to confirm which values are actually active.
